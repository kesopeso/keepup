What changes

Reduce the work on every screen.

Current · source inspection

Too much competes with the route.

  • Create exposes description, password, transport, and sharing options together.
  • The member sheet puts route information and owner actions before "Your access" and members.
  • Capability values such as "Can share: Yes" occupy space beside the actual controls.
  • The map displays a point counter and Auto/Manual labels.

Sources: create-route-form.tsx, join-route-screen.tsx, route-map.tsx, and globals.css. No current-screen screenshot was captured; Chrome inspection was unavailable.

Proposed · layout refresh

One clear action at a time.

  • Create starts with route name, your name, and transport. Show the sharing default; disclose optional settings.
  • Sharing and members lead the sheet. Route details and owner actions get a separate settings panel.
  • Replace capability readouts with available actions and concise explanations.
  • Remove the point counter from the main map. Keep viewport behavior and a clear "Fit group" action.

Desktop retains a large map beside a roughly 340px member panel. On phones, collapsing members gives more space to the map.

Route settings · Everyone can share

Your location stays private until you start sharing.

Make optional settings feel optional.

Keep the default sharing policy visible in the disclosure label. Password and description remain available without dominating the first screen. Keep field errors beside their inputs.

Join with only what's needed.

Show the route name and access requirements, then name and transport. Ask for a password only when required. Reuse saved profile values. Returning members keep their existing access.

Be explicit about location.

Creating or joining never starts tracking. Permission guidance appears when the member chooses to share. Keep the browser-open and battery/data guidance near that action.

Implementation proposal

Build it in reviewable steps.

Direction selected: full layout refresh.

The review selected the full layout refresh with no additional styling changes. Use the map-led route screen and simpler entry forms shown here. Use the current system font stack, 48px primary controls, 12px control corners, and 20px panel corners as the starting values.

Introduce shared controls and update create/join.

Define CSS tokens and reusable fields, buttons, status labels, and dialogs. Update globals.css and the create/join components. Preserve form payloads, browser identity, all seven transport modes, and authentication behavior.

Reorganize the live route screen.

Separate the header, sharing controls, member list, and settings presentation in join-route-screen.tsx. Update route-map.tsx controls. Reuse the map adapter and existing tile provider initially. Preserve manual pan/zoom and explicit refit behavior. Keep map attribution visible.

Finish states and validate the actual app.

Review 360px and 390px phones, landscape, and desktop at 1280px. Check keyboard operation, focus restoration, 200% zoom, contrast, reduced motion, safe-area insets, and long names. Run the web build and existing tests through Docker Compose. Update the owning product, frontend, and status docs with accepted changes.

States included in the refresh

  • Stale, offline, spectating, tracking, and left labels remain distinct. Preserve member color as identity; use text and icons for status.
  • Show a clear reason for view-only access, full tracking slots, blocked location, and connection failures.
  • Keep the blocking refresh recovery choice and duplicate-connection notice.
  • Archive uses the same layout with history, a closed label, and no sharing action.
  • Retain close confirmation and exact route-code confirmation for deletion in owner settings.
  • Include loading, empty map, invalid access, and failed form submission states.

Tradeoffs and boundaries

  • A layout refresh touches more JSX and focus behavior than a CSS-only change. Keep live state logic separate from presentation during the work.
  • Collapsing the sheet must resize the map correctly and keep sharing accessible. Start with a button; dragging can follow if needed.
  • The concept map is illustrative. Verify real map labels, paths, and markers outdoors before deciding on any tile style change.
  • No backend or data migration is expected. Saved member access and route links must continue to work.
  • Light mode, chat, replay, and transport changes remain deferred.
