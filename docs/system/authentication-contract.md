# Account API contract v1

This contract covers the implemented backend for the [authentication tasks](../planning/authentication-tasks.md). B2–B6 implement password/session, verification/recovery, Google, account route access, My routes, multiple viewers, exclusive sender leases and synchronous live revocation cleanup behind `AUTH_ENABLED=false` by default. Anonymous routes remain available only in legacy mode; account mode replaces the full route/socket surface. Web authentication/account settings are implemented in W1; web My routes/account route integration are implemented in W2; native authentication/account settings are implemented in A1. Native My routes/account route integration and release checks remain pending; do not treat API enablement as the production rollout.

The owner accepted the remaining product defaults on 2026-10-21. The [PRD](../product/authentication-prd.md) owns their meaning; [ADR 0001](../adr/0001-account-authentication.md) owns the architecture. [Deterministic examples](authentication-fixtures.json) identify the contract as `keepup.accounts.v1`. HTTP paths remain unversioned. This is a coordinated breaking client/API release, not compatibility with legacy member/owner tokens.

## Encoding and transports

Paths here are backend paths. Browser clients prepend `/api` through the existing proxy. JSON uses camelCase, UUID strings, UTC RFC3339 timestamps, and explicit booleans. Empty lists are `[]`; absent optional credentials are omitted, never `null`. Bodies are bounded to 4096 bytes, except the Google proof endpoint allows 16384 bytes. Unknown request fields and trailing JSON values fail with `400 invalid_input`. Confirmation fields stay in the client and are not transmitted. Never log request bodies, credentials, or query tokens.

All browser mutations, including login/signup and account route operations, require an exact configured `Origin`, `Content-Type: application/json`, and `X-KeepUp-Request: 1`. No wildcard/credentialed cross-origin access or preflight grant is provided for `/auth`, account `/routes` or `/me/routes`. Use `credentials: same-origin`. Responses use `Cache-Control: no-store`. This custom-header and origin policy is the CSRF defense, including login CSRF; SameSite is additional protection. See [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Web session credentials exist only in an HttpOnly, Secure, SameSite=Lax, Path=/, host-only `__Host-keepup_session` cookie in production. Development uses `keepup_session` without Secure. Signup/login/rotation return `{user, expiresAt}` with no raw credential; authenticated browser responses renew cookie expiry alongside server idle expiry. Browser JS never stores the credential. `GET /auth/me` may omit Origin for same-origin reads and renews expiry.

Native clients send `X-KeepUp-Client: native`, no Origin, Cookie, or browser fetch metadata, and authenticate with `Authorization: Bearer <sessionToken>`. Signup/login/rotation additionally return `sessionToken`; store it using platform secure storage. Mixed cookie/bearer or browser/native transports are rejected with `403 invalid_transport`. An untrusted Origin is rejected before service calls. Native requests do not use cookies.

`user` is `{id, email, username, verified}`. Both identifiers preserve their stored display casing. Internal session IDs, normalized lookup keys, hashes, and provider subjects are never response fields. Session idle expiry is server-authoritative, default 30 days. Requests that successfully authenticate and authorized live activity extend it. Expired/revoked credentials never revive. Explicit rotation atomically replaces the secret while retaining session ID, with no overlap/grace. Clients serialize rotation with other requests. No periodic background rotation is required in v1; password change rotates the current credential. A fresh password login creates a new independent session.

## Validation

Username is ASCII `[A-Za-z0-9_-]{3,24}` and is not trimmed. Email is a trimmed bare ASCII address, at most 254 bytes, parsed server-side; display names and non-ASCII mailboxes are unsupported in v1. Normalize email and username by lowercase for lookup, without stripping email dots or plus suffixes. Database unique constraints arbitrate concurrent registrations. Email and username have no mutation endpoint and a database trigger prevents changes.

Passwords have 8–128 Unicode code points, at least one ASCII digit and one Unicode punctuation or symbol. Whitespace alone is not a special character. Never trim, normalize, or truncate passwords. Login compares the original password exactly and does not impose signup composition rules on credential lookup. Argon2id PHC strings include salt/version/work parameters. Initial costs are 64 MiB, three iterations, one lane, a 16-byte random salt and 32-byte output, with two concurrent password operations per process. Tune costs with deployment measurements before release; the parser bounds stored costs before allocation. See [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Sessions and purpose tokens use 32 random bytes encoded as unpadded base64url. Credential records persist SHA-256 digests only. Queued email links are encrypted with AES-256-GCM and erased on terminal delivery/cancellation; the encryption key stays outside PostgreSQL. Use separate purpose records for verification, reset, Google flow, and socket tickets, rather than accepting one token type as another.

## Password/session endpoints

These endpoints are implemented when enabled. Signup atomically queues verification mail with the account/session; B3 supplies activation below.

| Method and path | Request | Success | Errors beyond common failures |
|---|---|---|---|
| POST `/auth/signup` | `{email, username, password}` | 201 session response, `verified:false` | 400 `invalid_input`; 409 `email_taken` or `username_taken` |
| POST `/auth/login` | `{identifier, password}` | 200 session response, active or pending | 401 `invalid_credentials`, identical for absent user/wrong password |
| GET `/auth/me` | session credential | 200 `{user, expiresAt}` | 401 `session_expired` |
| POST `/auth/session/rotate` | session credential, empty JSON object | 200 session response, old credential invalid | 401 `session_expired` |
| POST `/auth/logout` | session credential, empty JSON object | 204, clear browser cookie | 401 `session_expired` |
| POST `/auth/logout-all` | session credential, empty JSON object | 204, revoke all account sessions, clear cookie | 401 `session_expired` |

Pending sessions may call account, verification, recovery, and logout endpoints. The shared active-account guard rejects pending route requests with `403 email_verification_required`; B5 applies it to all account route entry points. Account live commands and outbound data recheck database authority, and an authorization timer runs at the configured WebSocket ping interval. Logout/reset/password change release affected sharing in the revocation transaction, then send advisory events and disconnect affected sockets before returning success. Password change retains the current session and its connections while revoking other sessions. Account sessions never authenticate legacy route sockets.

All error bodies have `{error:"stable_code"}`. Common failures: `400 invalid_input`, `401 session_expired`, `403 origin_rejected`, `403 csrf_rejected`, `403 invalid_transport`, `415 json_required`, `429 rate_limited` with integer-seconds `Retry-After`, and `500 internal_error`. Never expose driver errors. Login/account lookup must avoid disclosing account existence. Registration explicitly reports field uniqueness conflicts.

Initial fixed-window limits are configurable: login 20 attempts per 15 minutes per normalized identifier and source address, signup 5 per 15 minutes per source. Counters live in PostgreSQL so process restarts/replicas cannot bypass them. Forwarded addresses are ignored unless the socket peer is in configured trusted proxy CIDRs; traversal stops at the first untrusted hop. No counters contain raw email/IP values. Cleanup retains expired tokens/sessions/counters for seven days by default, covering all configured rate windows. See [delivery and proxy configuration](../workflow/authentication-email.md).

## Verification and password maintenance

B3 implements these endpoints. Token consumption requires explicit POST; a scanner GET has no effect. Email links carry tokens in URL fragments so server/proxy requests do not receive token query strings. Clients must hold tokens in memory, exclude analytics, and remove the fragment. W1 implements web link pages and removes fragments immediately after capture; A1 implements native handling through the local Expo module, clearing in-process Activity Intent data after capture. Web and native confirmation matching are implemented. The API rejects extra confirmation fields.

| Method and path | Request / authority | Success |
|---|---|---|
| POST `/auth/verification/resend` | pending session, `{}` | 202 `{status:"accepted"}` after transactional queueing |
| POST `/auth/verification/confirm` | `{token}`, no session required | 200 `{status:"verified"}`, no session/cookie issued |
| POST `/auth/password/forgot` | `{identifier}` | 202 `{status:"accepted"}` regardless of account existence |
| POST `/auth/password/reset` | `{token,password}` | 204 after consuming token and revoking all sessions; no login or activation |
| POST `/auth/password/change` | active session, `{currentPassword,password}` | 200 rotated session response; other sessions revoked |

Verification TTL 24h, reset TTL 1h, resend cooldown 60s, max five messages per account per hour and 20 per source per hour. Token confirmation attempts are capped at 20 per source per 15 minutes. Invalid, consumed and superseded links return `400 invalid_token`; expired links return `400 token_expired`. Responses never identify another account or consume a link on failed password validation. Replacement and consumption are atomic. Password change errors use `401 invalid_credentials` without dropping a valid current session.

Password change also invalidates outstanding reset links. Account-specific recovery cooldowns/quotas are hidden behind the accepted response. Known/unknown/suppressed recovery requests have a configurable 200ms minimum response duration, which reduces routine timing differences without promising constant-time operation under load.

The mail provider interface accepts an ID, recipient and rendered message. SMTP and fake delivery implement it. An encrypted outbox row is written in the same transaction as the new token. The worker retries after 1m, 5m, 15m, 1h, 4h, stopping after five retries, expiry, or supersession. Account locks serialize token replacement/consumption with bounded delivery; SKIP LOCKED coordinates workers. SMTP delivery is at least once, so an acknowledgment/commit failure can duplicate an email. Tokens remain single-use. Terminal rows erase ciphertext. All TTLs, cooldowns, windows, attempt limits, and retry schedule are [deployment settings](../workflow/authentication-email.md). Provider failure does not activate accounts. Manual resend can replace a failed message after cooldown. Gmail configuration and real delivery remain R1.

## Google proof and onboarding

B4 implements server-issued nonce flows, default TTL 10m. Web uses a separate HttpOnly host-prefixed `__Host-keepup_google` flow cookie, or `keepup_google` in development; native uses an opaque flow credential in secure transient storage. These contexts cannot access account or route sessions. Deadlines never extend with polling or resend. Do not persist onboarding passwords in the flow. Google is unavailable with `503 google_unavailable` until the transport's client IDs are configured. See [Google configuration](../workflow/authentication-google.md).

1. POST `/auth/google/start`, `{}` returns `{nonce,expiresAt}`; native also receives `flowToken`. Bind allowed client audience and nonce in server state. Native subsequent flow calls use `Authorization: Bearer <flowToken>`; web uses its flow cookie.
2. POST `/auth/google/proof`, `{idToken}`, validates signature/issuer/audience/expiry/nonce and consumes the proof step once. Existing linked subjects or an active same-email account with authoritative ownership return `{status:"authenticated",...sessionResponse}`. Unknown identities return `{status:"onboarding",email,expiresAt}`. Third-party Google emails return `{status:"email_verification_required",expiresAt}` after queueing a KeepUp challenge.
3. POST `/auth/google/complete`, `{username,password}`, atomically creates account/password/provider binding for an onboarding context, returning `{status:"authenticated",...sessionResponse}`. Existing active accounts never have their password overwritten, including accounts activated during onboarding. Pending password registrations require this fresh password setup after ownership is established, retain their immutable username and revoke all previous pending sessions and verification/reset links. Their onboarding response includes `username`; submit that value, matched case-insensitively, while stored display casing stays fixed.
4. POST `/auth/google/email/confirm`, `{token}`, confirms third-party email ownership without signing in that browser. The initiating context polls GET `/auth/google/context`, then POST `/auth/google/exchange`, `{}`, to obtain an existing-account session or proceed to onboarding. Flow completion is single-use and remains bound to the initiating context. Resend POST `/auth/google/email/resend`, `{}`, uses B3 limits.

Flow GET returns `{status:"awaiting_proof"|"onboarding"|"email_verification_required"|"ready",email?,username?,expiresAt}`. Never return credentials on GET. Proof/exchange onboarding responses include email, and challenge responses may include it. Email confirmation returns `200 {status:"verified"}` without cookies; resend returns `202 {status:"accepted"}`. Bad proof uses `401 invalid_google_credential`; consumed/expired context `400 invalid_flow` / `400 flow_expired`; provider conflict `409 identity_conflict`; username conflict retains onboarding. Password/signup collisions and email challenges serialize with external-identity uniqueness. Provider subject remains identity after linking even if Google email changes. Web completion clears its flow cookie; native clients discard the flow credential. Cancellation discards the client flow, leaving server cleanup to expiry.

The maintained `go-oidc` verifier validates Google RS256 signatures, issuer and expiry. The adapter checks every audience against the flow's stored transport allowlist, approved `azp` when present, verified email, subject and issuance time. The service compares the nonce digest and consumes proof state under a database lock. Raw proofs and flow credentials are never persisted. Google start/proof/complete/exchange share the configured login-attempt budget per source in a separate Google scope. Challenge issuance shares B3's source/recipient mail limits and recipient-wide Google cooldown; confirmation uses B3 confirmation limits. Tokens are purpose-bound to their original flow, expire no later than its deadline, and use the encrypted queue. OAuth redirect/code callbacks are not implemented; any future redirect variant additionally requires state and PKCE. Clients must not replace validated ID-token proofs with arbitrary profile JSON.

## Account route API

B5 implements these endpoints when `AUTH_ENABLED=true`. All `/routes` endpoints require active account sessions, including `/routes/{code}/access` and archives. Create/join bodies drop `clientId` and `displayName`; even empty legacy fields are rejected. Responses drop `memberToken`/`ownerToken` and `clientId`. Ownership, current membership and display names come from account authority. Members and snapshot members add `userId`; their `id` remains the membership episode ID used by historical paths. No email appears in route payloads. A restored current membership is idempotent and bypasses repeated route-password/transport entry; explicit leave/rejoin creates a new episode while retaining history. Owners cannot leave an active route.

Create accepts `{name,description?,password?,sharingPolicy,transportMode}` and returns `201 {route,owner}`. Join retains POST `/routes/{code}/members`, accepts `{password?,transportMode?}`, and returns `201 {route,member}`. A new or returning-after-leave episode requires a valid transport mode; restoring a current membership may submit `{}` and does not emit another member-joined event. PATCH keeps `{name?,description?,status?}` with only the closed transition supported. DELETE route/membership may omit the body or submit `{}`, while retaining the JSON content type for the transport guard. Ticket issuance requires `{}`. Unknown fields, trailing JSON and bodies over 4096 bytes are rejected.

Missing/invalid sessions return `401 session_expired`; valid sessions without current membership or ownership receive `403 unauthorized`; wrong route passwords return `401 invalid_password`; missing/deleted/legacy-only routes return `404 route_not_found`; archived live actions return `409 route_closed`. Access metadata is available by code to verified accounts without membership, for the join screen; snapshots and path history require current membership. Ownership is retained if an owner leaves a closed route, allowing edit/delete, but archive reading still requires explicit rejoin. Such an owned summary has relationship `owner` and action `rejoin` until membership is restored.

Migration 0006 keeps account route ownership and membership separate from legacy rows, with one current membership per account/route. Account mode hides legacy-only routes; legacy mode cannot access or join account-owned routes, even after the feature flag is switched off. It never converts existing data or grants route access from old credentials. The down migration refuses to remove account authority while account-owned route data exists; handle that data explicitly in the later maintenance/rollout plan.

GET `/me/routes?view=active&owned=true&joined=true&left=false&limit=20&cursor=...` returns `{items,counts:{active,archived},nextCursor}`. Defaults match the URL shown. `view` is `active` or `archived`, booleans must be literal `true`/`false`, limit 1–100. Malformed filters/cursor use `400 invalid_input`. All filters false yields empty items and zero counts. Counts use selected categories before pagination. Categories are mutually exclusive: owner first, current non-owner next, former without current membership last.

Each item is `{id,code,name,status,relationship,hasPassword,createdAt,closedAt,action}`; relationship `owner|joined|left`, action `open|view_archive|rejoin`. `closedAt` is null while active. Share URLs are constructed from the configured public route base and code, without credentials. Former-member rows contain no description, membership list, points, passwords, or privileged details. Deleted routes are omitted.

Sort active by `(createdAt,id)` descending and archives by `(closedAt,id)` descending. Opaque HMAC-signed keyset cursors bind account, view and filters; they never grant access. The signing key is derived separately from the deployment outbox key; rotating that key invalidates existing cursors. Unknown/duplicate query parameters, nonliteral booleans and malformed/tampered/cross-account cursors return `400 invalid_input`. Concurrent list changes may alter totals; clients must deduplicate by route ID when appending. Filter changes restart pagination. A fresh visit uses Active/default filters; back navigation restores view/filter/loaded position within the same signed-in session; logout/account switch clears it. W2 implements these web UI state rules; native A2 remains pending.

Left active routes require a new join/password check. Left closed routes also require joining for archive access, creating an archive-only membership episode with no sharing rights. Restoring a current membership bypasses repeated route-password entry. Recheck access on every open; a cached dashboard never grants membership. Browser/native protected destinations are local allowlisted paths or typed route intents, never arbitrary URLs. Preserve them separately from secrets through onboarding and verify access before navigating; fallback `/my-routes` when absent/unavailable.

## Live account protocol

B5 implements POST `/routes/{code}/socket-ticket`, `{}`, returning `{ticket,expiresAt}` after active-session/membership checks. Default TTL 30s, configurable by `AUTH_SOCKET_TICKET_TTL`. Ticket digests bind session, route and membership episode, and consume atomically on the first WebSocket frame `{type:"authenticate",ticket}`. Bootstrap rechecks the session, route lifecycle and exact current membership episode. Replay, expiry, leave/rejoin and revocation reject the ticket. No URL credential, legacy member token or archive socket is accepted. Native upgrades send `X-KeepUp-Client: native` without Origin/Cookie/Authorization; browsers need an exact configured Origin. The upgrade does not use session cookies as authority. First frames are bounded to 4096 bytes and reject unknown fields/trailing JSON. Existing first-frame timeout and ping/pong settings remain. Expired ticket rows use the account retention/cleanup worker.

Account commands, outbound events and periodic authorization checks revalidate session/current membership. GPS validation and historical segments remain in force. B6 implements the following protocol with independent persisted viewer connections and account/route sharing leases. Legacy mode retains its separate single-connection protocol.

`connection_established` adds `connectionId` and `viewer` capabilities. Allow multiple viewers per membership. `start_sharing` retains `{type,requestId}` and atomically acquires the account/route lease; `command_ack` for start adds `sharingGeneration`. Every `position_update` and `stop_sharing` carries that generation. The server also binds session/connection ID, so knowing a generation cannot grant sender authority. The member/route events retain their existing shapes except account-backed identity fields and the start generation only in the submitting connection's acknowledgment.

A second sender receives `{type:"command_rejected",requestId,command:"start_sharing",reason:"sharing_on_another_device"}`. Retrying Start on the owning connection returns the same generation without renewing the sender deadline or opening another segment. Viewers have `canStopSharing:false` for another device. REST snapshots have no sender connection authority, so `canStopSharing` is always false there. `viewer_updated`, `{type,viewer}`, refreshes connection-specific capabilities after room events. Old-generation packets receive `position_rejected` / `command_rejected` with `sharing_expired`, without changing state. Account revocation sends `{type:"session_revoked",reason:"logout"|"logout_all"|"password_reset"|"password_changed"}`, then closes with code 1008. Events are advisory; committed database revocation is authoritative and checked before further commands/points.

Sender disconnect marks only that sender stale. Existing 20s position-stale, 5m stale-to-offline and 20s spectator grace defaults remain configurable. Viewer activity cannot refresh a sender lease; only accepted GPS samples renew its position deadline. Deadline checks run at most one second apart, or faster for shorter configured intervals. Stop/offline/revocation/leave/close/delete releases the lease and closes its segment. At sender expiry, surviving viewers retain spectating presence; without viewers the member becomes offline. Generation and route locks fence late messages, disconnects and deadline checks. Different routes permit separate senders from the same account. Reconnect creates a viewer and never adopts another connection's lease or restarts location capture.

Migration 0007 persists connections, leases, absence deadlines and revocation reasons. Startup recovery closes abandoned account segments, clears account connections/leases and marks current account memberships offline before HTTP serving; it preserves route history and legacy live state. A dedicated PostgreSQL advisory lock permits one account live runtime per database/schema. A second API process fails startup instead of resetting an active runtime. Lock loss disables account operations and triggers API shutdown. Horizontal replicas require a distributed live-event transport before removing this restriction. Runtime setup and shutdown live in the API entry point; no migrations run automatically.
